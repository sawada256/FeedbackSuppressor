## 研究の比較

| 研究・方式 | 要点 | 適用判断 |
|---|---|---|
| Mounir・Bernardi・van Waterschoot, 2025：NINOS²-T | 同じ周波数のSTFT値が時間方向に持続するかを、正規化した逆スパース性で評価する。音量自体を特徴から外し、早期ハウリングやringingを対象にする。 | 主な参考。全体音量に依存しない時間特徴を採用する。持続する楽器音もあるため、単独の指標としては使わない。 |
| Alkaher・Cohen, 2022：Temporal Howling Detector | 振幅の時間的な傾きの偏差による候補検出に、誤警報を除く段階を組み合わせる。対象は音声拡声。 | 成長する候補の確認を速め、誤検出確認を別条件にする考え方を採用する。音楽への性能をそのまま外挿しない。 |
| Zhang・Yu・Yu, 2023：Deep AHS | Teacher forcingを用いて学習したattention付きRNNでマイク音から目的信号を取り出す。検出してノッチを置く方式とは異なる。 | 今回は不採用。学習モデル・学習データ・実時間推論基盤がなく、ライブ音楽の音色保存を別途評価する必要がある。 |
| 従来のPNPR／PHPR／IPMP | 周辺帯域比、倍音比、フレーム間のピーク持続を利用する。全体の最大ピークだけを選ぶ手法は、弱いハウリングを候補から除外し得る。 | 周辺比と倍音構造を補助条件に使う。全体音量より大きいこと、全体の上位数個に入ることは必須にしない。 |

出典： [NINOS²-T原著・従来方式の整理](https://link.springer.com/article/10.1186/s13636-025-00399-1)、[Temporal Howling Detector著者所属機関の要約](https://cris.technion.ac.il/en/publications/temporal-howling-detector-for-speech-reinforcement-systems/)、[Deep AHS原著](https://arxiv.org/abs/2302.09252)。

## 採用するアルゴリズム

既存のIIRノッチによる音声パスは維持し、Advanced／Aggressiveに**相対スペクトル・時間的持続・位相安定・倍音保護を組み合わせた検出器**を実装する。この入力・出力だけのプラグイン構成と低遅延の要求に最も適するという設計判断であり、すべての場面で最適という主張ではない。音響伝達経路を同定するAFCは、参照信号、経路モデル、音楽との相関による推定の偏りの対策が必要になるため、今回の変更には含めない。

1. **ステレオ解析**：左右を独立にFFTし、各ビンの強い方のパワーを用い、約35 msの指数平滑化で雑音によるピークの揺れを抑える。位相履歴も左右独立に保持する。逆相のハウリングや片chのピークがモノ加算で消えない。ノッチは既存構成に合わせて両chへ適用する。
2. **背景との相対比較**：±14ビンの範囲からピーク近傍±2ビンを除外する。背景の上位25%を除き、残りを線形パワーで平均する。全体のRMSや固定1/fカーブを弱いピークの必須条件にしない。起動時に低すぎる時間フロアを背景として使う処理を廃止する。
3. **倍音構造の保護**：補間した周波数を基準に、整数倍・分数倍のピークを調べる。候補を1〜8次の倍音と仮定して基本周波数を探し、同じ基本周波数に対応する位相の安定したピークが他に二つ以上ある場合に音楽由来として保護する。一つの偶然の一致で候補を捨てない。ハウリングが楽器の倍音列と重なる場合は検出しにくくなる。
4. **時間方向の確認**：平滑化前のSTFTから保存した16フレームの線形振幅から `N = ((Σa²)^0.5 / (Σa⁴)^0.25 - 1) / (16^0.25 - 1)` を算出する。持続性の補助特徴であり、原著のログ振幅・HDF・全ビン評価の完全再実装ではない。周波数の揺れと、約85 ms分（48 kHzでは8フレーム、96 kHzでは16フレーム）の位相差の円統計PLVも確認する。補間周波数と位相差からの平均周波数推定を併用し、隣接ビンにピークが移る場合も同じ時間追跡を続ける。PLVは音響ループの証明ではなく、楽器の持続音でも高くなり得る。
5. **成長／定常の二経路**：成長中は短めの確認時間、定常状態は長めの確認時間を要求する。Aggressiveは弱い候補を短めに確認する。持続時間をmsで扱い、サンプルレートによる不必要な変化を避ける。
6. **必要な減衰だけを追加**：EQ後・リミッター前の信号で残存ピークを確認する。初期カットは候補の突出量に応じて3〜9 dB（Standardは最大12 dB）。再検出による深掘りは150 ms以上間隔をあけて3 dBずつ。ノッチの平滑化はサンプルレートに依存しない約10 msの時定数にする。
7. **状態管理**：音楽保護の確認を通過したピークだけを出力する。解析FIFOが満杯なら未読データを上書きせず、欠落後に履歴を捨てる。手動Lock／Bypassのフィルタを深くしない。Soundcheckで作るFixedは周波数を固定し、明示的にLockするまでは必要な追加減衰を許す。このLock状態をセッション復元時も保持する。すべてロックされたフィルタ枠を勝手に再利用しない。

### モードと初期条件

| 条件（Sensitivity=0） | Advanced | Aggressive |
|---|---:|---:|
| 周辺背景に対する突出 | 7 dB | 5 dB |
| イベント時の位相PLV | 0.78 | 0.74 |
| 成長中の最短確認 | 130 ms | 90 ms |
| 定常候補の最短確認 | 350 ms | 220 ms |
| 定常時の時間特徴N | 0.92 | 0.90 |

成長経路は過去16フレームと現在のdB振幅に直線回帰を行い、区間あたり2 dB以上増加（Growth=Medium）、決定係数R²が0.75以上、Nが0.55以上、PLVが0.90以上の状態が成長確認時間にわたって続くことを要求する。一つの過去の雑音谷との差だけを成長と見なさない。候補を追跡中は突出条件に2 dBのヒステリシスを設けるが、検出イベントの発行時は元の突出条件を満たす必要がある。確認フレームのPLVは0.72以上を要求する。一時的なマスキングでは、同じ周波数でPLVが0.60以上、突出条件の不足が4 dB以内の場合に、蓄積した確認時間から1 hop分の証拠を減らす。このフレームでは確認時間を増やさない。特徴履歴の準備、FFT窓の2048サンプル、hop=512、周波数安定の確認も加わるため、表は実際の検出時間の保証値ではない。音声パスの追加バッファ遅延0と検出応答時間は別の数値である。3 msの遅延オプションではこの検出時間全体を先読みできない。

High／Low Focusは対象帯域の突出しきい値を2 dB下げる。音楽モードの絶対ピーク下限は約-75 dBFS（FFT振幅基準）、フレームRMS下限は-80 dBFS。Sensitivityを上げると突出条件が下がり、下げると厳しくなる。-60 dBでのクリップ近傍限定動作はStandardの仕様であり、Advanced／Aggressiveは相対条件を主とする。

新規インスタンスはAdvancedを初期選択する。パラメータIDと選択肢の番号は変えず、保存済みStandard等の選択はそのまま復元する。イベント発行には `confidence = 0.65 N + 0.20 PLV + 0.15 clamp((突出量 - しきい値)/12, 0, 1)` がAdvancedで0.76以上、Aggressiveで0.78以上であることも要求する。位相の条件だけを強くしすぎると、背景雑音中の弱い純音を見逃すため、時間的な安定性を重くする。おすすめの開始条件はAdvanced、Music、Sensitivity=0、Q=35〜60。弱いピークを見逃す場合にAggressiveを試す。音色が削られる場合は感度を下げるか、サウンドチェックで固定したフィルタを使う。

## 検証の範囲と限界

`tests/music_detection_test.cpp` は固定seedの広帯域ノイズと220 Hzの6倍音からなる合成音楽に、2371 Hzの弱い純音を混ぜる。純音振幅0.01、合成音楽のRMSに対して約-27 dBの成分、入力ゲイン差20 dB、44.1／48／96 kHz、逆相ステレオを比較する。音楽のみ、ビブラート、短い音、複数ピークとFFTビン境界のピーク、EQ後の残存検出、ロック枠・FIFO・リセットも検証する。既存DSPテストはReleaseでもassertを有効にし、CTestに登録する。別途、伝搬遅延と共振帯域を持つ模擬音響経路へ出力を帰還させ、閉ループの安定化を確認する。

実録音、実機マイクとスピーカーの閉ループ、会場の残響、クリッピング、意図的なギターフィードバック、多様な楽器音での性能は別途評価が必要。単一入力の音声だけでは、倍音の少ない安定したシンセ／フルートと定常ハウリングを完全に区別できない。二つ以上の倍音関係があるハウリングも保護対象に入ることがある。2048点FFTなので96 kHz時の低域分解能も粗くなる。無誤検出や実会場での利得増加は保証しない。

音声処理とUIのフィルタ状態共有には既存のmutexが残っている。今回、検出パラメータをatomic化し解析FIFOの読み書き所有権とライフサイクルを修正したが、全音声処理のwait-free化やCPU負荷保証までを行ったものではない。


## 検証結果（2026-10-06）

Releaseの `music_detection_test` による測定。純音は音楽開始から0.5秒後に加え、下表は純音開始から最初の検出までの時間。両モードで合成音楽の他の周波数は検出されず、入力を20 dB下げた場合も同じ応答だった。周波数誤差はこのテストの最終検出で0.5 Hz未満。録音や会場での平均性能の値ではない。

| サンプルレート | Advanced | Aggressive |
|---|---:|---:|
| 44.1 kHz | 394 ms | 255 ms |
| 48 kHz | 385 ms | 247 ms |
| 96 kHz | 423 ms | 295 ms |

- 同じ合成音楽のみ、ビブラート、45 msの短い純音では検出イベント0。
- EQ後の残存監視では、約9.2 dB／7.9 dBのカット（Advanced／Aggressive）で新しい検出が止まり、最大カット20 dBまで不要に深くならなかった。
- 遅延256サンプル、2250 Hz共振、帰還係数1.08の模擬音響経路では、抑制有効時の最後の1秒の共振帯域RMSが無効時より約56.6 dB低下した。これはこの単純なモデルでの減衰量であり、会場でのgain-before-feedbackの改善量ではない。
- さらに弱い振幅0.006（約-31 dB、48 kHz、Advanced）は検出に1.324秒かかった。同じ振幅の96 kHzでは今回の試行中に検出できず、極めて弱い成分の全サンプルレートでの早期検出は保証しない。実装・テストを音楽から約-27 dBの主検証条件と、この難しい境界条件に分けて評価した。
- FIFO過負荷後の復帰、リセット後の無音、複数ピーク、FFTビン境界のピーク、バッチ検出のカット制限、Lock／Bypass、ロック済み枠の保護も通過。

### 再現コマンド

既存 `build` のXcodeのパスが現在のマシンに存在しなかったため、別ディレクトリに現在のCommand Line ToolsでReleaseビルドを構成した。JUCEは既存の取得済みソースを使用した。

```bash
cmake -S . -B build-research -G Ninja \
  -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_C_COMPILER=/Library/Developer/CommandLineTools/usr/bin/clang \
  -DCMAKE_CXX_COMPILER=/Library/Developer/CommandLineTools/usr/bin/clang++ \
  -DFETCHCONTENT_SOURCE_DIR_JUCE="$PWD/build/_deps/juce-src"
cmake --build build-research --parallel 3
ctest --test-dir build-research --output-on-failure
```

他の環境ではコンパイラとJUCEソースの指定を外して通常のCMake構成を利用できる。生成物は `build-research/FeedbackSuppressor_artefacts/Release` 以下のVST3／AU／Standalone。既存プラグインのインストール先にはコピーしていない。

既存12項目のDSP検証と音楽検出回帰テストを含むCTestは2/2件通過（Release）。VST3／AU／StandaloneのReleaseビルドも成功し、VST3はJUCEヘルパーによるmoduleinfo.jsonの生成まで確認した。生成バイナリはarm64／x86_64のUniversal Binary。DAW上でのロード・実機音声入出力・実会場での試聴は未検証。
