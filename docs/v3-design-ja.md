# Feedback Suppressor V3 設計資料

作成日：2026-10-24。対象：`Feedback Suppressor V3`（プラグインコード `Fdb3`、バンドルID `com.liveaudiolab.feedbacksuppressorv3`、バージョン 3.0.0）。V2（`Fdb2`）と同時にインストールして併用できます。

この資料では、調査の要約と出典、V2 で見つけた不具合、V3 で変えたアルゴリズム、V2 と V3 の測定値の比較を説明します。数値はすべて合成信号による測定です。実際のマイク・スピーカー・会場で同じ性能になるとは限りません（§6）。

---

## 1. 調査の要約

### 1.1 ハウリング対策の分類（van Waterschoot & Moonen, 2011）
van Waterschoot と Moonen のサーベイは、ハウリング対策を次の4つに分けています。

1. **位相・周波数を変える方法**：周波数シフト、位相変調など。
2. **ゲインを下げる方法**：自動イコライザ。**NHS（notch-filter-based howling suppression）**はこのグループに含まれます。
3. **空間フィルタ**：ビームフォーミングなど。
4. **ループ経路を推定して打ち消す方法**：AFC（適応フィードバックキャンセル）。

本プラグインは、1入力1出力のインサートで使い、遅延0を目標としています。この条件で実装できる方法は NHS が中心です。AFC にはスピーカーへの参照信号とループ経路のモデルが必要です。さらに、音楽のように自己相関が強い信号では推定に偏りが出る問題があり、今回は採用していません。

### 1.2 NHS の検出基準
van Waterschoot と Moonen（JAES 2010）は、NHS を「検出」と「ノッチ設計」の2段階に分けています。検出に使われる特徴量は次のとおりです。

| 基準 | 内容 | V3 での扱い |
|---|---|---|
| PTPR（Peak-to-Threshold） | ピークの絶対レベル | Classic モードの絶対値ゲートとして残しています。音楽対応モードでは床としてだけ使います |
| PAPR（Peak-to-Average） | フレーム平均との比 | 使いません。弱いハウリングを見逃すためです |
| **PNPR**（Peak-to-Neighbouring） | 近傍ビンとの比 | 「突出量」として使います。±14 ビンのうち下位75% の線形パワー平均と比べます |
| **PHPR**（Peak-to-Harmonic） | 倍音・分数倍音との比 | 「倍音ファミリー保護」として使います |
| PMP / IPMP（ピーク持続） | フレーム間でピークが続くか | トラック持続時間として使います |
| **IMSD**（Interframe Magnitude Slope Deviation） | フレーム間の振幅傾きのばらつき | 4／8／16 フレームの回帰の傾き（dB/s）と決定係数 R² として使います |

同論文の比較では、単独の基準よりも、PHPR・PNPR・IMSD のように性質の違う基準を組み合わせたほうが性能が良いとされています。V3 もこの方針で、突出量・倍音構造・成長の一貫性・周波数の安定性を組み合わせています。

### 1.3 ノッチの設計と解除
- **市販機の公開仕様**：dbx AFS2 は Fixed／Live フィルタを分け、Live にはリフト（自動解除）があります。音楽設定では、約930 Hz 未満のノッチを Q ではなく固定幅（8 Hz）にしています。Shure DFR22 は浅いノッチから始め、ハウリングが残る場合に深くします。
- **適応ノッチフィルタ（ANF）**：Gil-Cacho ら（2009）は、正則化した ANF でハウリング周波数を追従する方法を示しています。V3 はこれを部分的に取り入れ、検出イベントごとにノッチの中心周波数を検出値の方向へ半分だけ動かします。追従は滑らかに行います。
- **FIR 型ノッチ**：区分ノッチフィルタ（Sensors 2021）は位相歪みを抑える代わりに遅延が増えます。遅延0という要件に合わないため採用していません。

### 1.4 精密な周波数推定
- 3点 DFT 補間（Jacobsen & Kootsookos 2007、Candan 2011）は、FFT サイズを大きくせずにビン幅より細かい周波数を推定する方法です。
- 位相ボコーダ（連続フレーム間の位相進みの偏差）は、定常な正弦波ならさらに精密です。V3 は8フレーム（約85 ms）の位相差を円平均し、その結果を主な推定値にしています。PLV（位相固定値）が低いときは、対数振幅の2次補間を使います。測定した誤差は §5.3 を参照してください。

### 1.5 音楽・歌とハウリングの区別
- NINOS²-T（Mounir ら, 2025）は、時間方向のスペクトルの持続性を、音量に依存しない形で評価する特徴量です。V2 から定常経路の補助特徴として使っています。
- 音だけでハウリングと区別しにくい音として、倍音の少ない持続音（フルート、シンセ）と、まっすぐ伸ばした歌声があります。V3 は次の3点で区別します。
  1. **周波数の揺れ**：ハウリングの周波数は 0.1 Hz 単位で安定しています。人の声や生楽器にはビブラートやピッチのドリフト（0.2〜1 %）があります。
  2. **単独での指数的な成長**：ハウリングは他の成分と無関係に一定の dB/s で大きくなります。音の立ち上がりやクレッシェンドでは、スペクトル全体が一緒に変化します。
  3. **倍音関係**：音符には整数比の倍音が伴います。
- **周波数シフト**（Schroeder 1964）は数 dB の安定化マージンが得られます。ただし音程が変わるため、ボーカルのモニター用途には不向きと判断し、採用していません。

## 2. V2 で見つかった不具合と V3 での修正

| # | 不具合（V2） | 影響 | V3 の修正 |
|---|---|---|---|
| 1 | 音声スレッドの `processAudio` と `updateTimers` が `std::mutex` をロックしていた。UI（40 Hz の描画、10 Hz の表）と検出スレッドも同じ mutex を使っていた | 音切れ（ドロップアウト）や優先度逆転の危険 | 音声スレッドはロックしない設計にしました。ノッチの目標値はスロットごとの seqlock で受け渡します。タイマー処理は解析スレッドへ移しました |
| 2 | `processBlock` のたびに `updateParameters()` を呼び、その中で `setDefaultQ` などが mutex をロックしていた | 同上 | パラメータの反映は解析スレッドで行います。音声スレッドは atomic を読むだけです |
| 3 | `setLatencySamples()` を音声スレッドから呼んでいた | ホストによっては動作が不安定になる | 解析スレッドが変化を検出し、AsyncUpdater 経由でメッセージスレッドから報告します |
| 4 | 3 ms の Lookahead がノッチより前で音声を遅らせるだけだった（検出には数十 ms かかる） | 遅延が増えるだけで効果がない | 3 ms はパニックリミッターの先読みに使うよう変更しました。ピークが出力される前にゲインを下げ終えるので、オーバーシュートやハードクリップが起きません。遅延の切り替えは 3 ms のクロスフェードで行います |
| 5 | ホストのバイパス中に遅延がなくなる | ホストの遅延補正とずれる | `processBlockBypassed` でも同じ遅延をかけます |
| 6 | 削除、Clear、フィルタ単位の Bypass、Bypass モードで、ノッチをカスケードから即座に外していた | クリック音 | ゲインを約10 ms で 0 dB に戻してから停止します。テストで確認済みです（§5.5） |
| 7 | 解放したスロットを再利用すると、ノッチが古い周波数から新しい周波数へスイープする | 一瞬、別の周波数が削られる | ゲインが0のフィルタは、新しい周波数から直接立ち上がります。完全に消えたスロットを優先して割り当てます |
| 8 | ビクアッドの係数を1サンプルごとに再計算していた（cos/sin/pow）。float で状態を保持していた | CPU 負荷。低域の狭いノッチで精度が落ちる | 係数は16サンプルごとに更新し、対数領域で補間します。状態と係数は double で保持します |
| 9 | 低域のノッチ幅が狭すぎる（Q 35 で 100 Hz なら 2.9 Hz 幅） | 周波数誤差やモードのずれで効かない | 自動ノッチの最小帯域を 4 Hz にしました（Q ≤ f/4） |
| 10 | 状態の復元で `snapshots.back()` によって ID を推測していた。固定フィルタを含まないプリセットを読んでも古い固定フィルタが残った。APVTS のツリーに FixedFilters 子要素が混ざっていた | 復元結果の取り違え | `addFilter()` が ID を返すように変更しました。復元時は固定フィルタを入れ替えます。子要素は分離してから APVTS を復元します |
| 11 | 96 kHz では 2048 点 FFT のビン幅が 47 Hz になり、ホップ時間も変わっていた | サンプルレートによって性能が変わる | 88.2 kHz 以上は整数比で間引き、44.1／48 kHz で解析します |
| 12 | スペクトル表示の EQ カーブを、解析側のサンプルレートで計算していた | 96 kHz ではカーブの位置がずれる | フィルタ側のサンプルレートで計算します |
| 13 | NaN や Inf がビクアッドの状態に入ると、その後ずっと無音になる | 復帰できない | 状態をチェックしてリセットします。リミッターは入力の NaN を 0 として扱います |
| 14 | 無音のホップごとに約300 KB の履歴を毎回クリアしていた | 無駄な CPU 使用 | 一度クリアしたら、それ以降はスキップします |
| 15 | 「Standard (Safe)」という名前なのに、歌に対する誤検出が最も多かった（§5.2） | 分かりにくい名前 | 「Classic (Legacy)」に改名しました。おすすめは Advanced です |
| 16 | 解析スレッドがコンストラクタから起動していた（prepare 前） | 不要なスレッド | `prepareToPlay` で起動します |

## 3. V3 の検出アルゴリズム（Advanced / Aggressive）

解析条件：44.1／48 kHz、2048 点の Hann 窓、ホップ 512（75 % 重なり）、左右独立の FFT。各ビンで大きい方のチャンネルのパワーを使い、35 ms で平滑化します。

ピークのビンごとに、次の順で処理します。

1. **ゲート**
   - 突出量（PNPR）が 7 dB 以上（Aggressive は 5 dB）。Sensitivity を 1 dB 上げると、しきい値が 0.35 dB 下がります。
   - PLV ≥ 0.72。
   - 絶対レベル ≥ −75 dB。
   - フレーム内で最も大きい成分から 45 dB 以内（追跡の条件）。
2. **倍音ファミリー保護（PHPR）**
   - 位相がそろった整数比の関係（相対誤差 0.4 %）にある成分が2つ以上あれば、音符と判断して除外します。
   - 関係する成分が1つだけ（−12 dBFS 未満）の場合は、遅い成長経路と定常経路だけを止めます。速い指数成長は通します。
3. **トラック**
   - 隣接ビンのアンカー周波数を引き継ぎます。
   - 短いマスキングで途切れた場合は、最大3フレームまで「ゴースト」としてトラックを維持します。
4. **周波数安定エンベロープ**
   - 位相ボコーダ周波数の最小値と最大値を、時定数 250 ms で現在値に近づけながら更新します。
   - 幅が `max(1 Hz, 0.06 %·f) + 21/SNR` 以内なら安定と判定します。
   - ビブラートやピッチドリフトがあるとエンベロープが広がり、不安定と判定されます。
5. **成長（IMSD 系）**
   - 平滑化したスペクトルに対し、8フレームと16フレームで回帰を行い、傾き（dB/s）と R² を求めます。
   - 自分の主ローブ（±3 ビン）を除いた残りのスペクトルの成長を差し引いた「相対成長」を使います。音の立ち上がりやクレッシェンドでは全体が一緒に成長するため、相対成長が小さくなります。
6. **イベントを出す3つの経路**

| 経路 | 条件（Growth=Medium、Advanced） |
|---|---|
| 速い成長 | 8フレームの傾き ≥ 25 dB/s、R² ≥ 0.85、相対成長 ≥ 15 dB/s、直近4フレームの傾き ≥ 12.5 dB/s が3フレーム連続。かつ上昇量 ≥ 4 dB、強い位相（PLV ≥ 0.9 の累計）≥ 60 ms、周波数が安定 |
| 遅い成長 | 16フレームの傾き ≥ 6 dB/s、R² ≥ 0.75、8フレームの傾き ≥ 16フレームの傾きの半分（立ち上がりで膨らんだ傾きを除外）、相対成長 ≥ 3.6 dB/s、上昇量 ≥ 3 dB、時間スパース性 N ≥ 0.5、強い位相 ≥ 100 ms、周波数が安定、倍音関係の成分なし |
| 定常 | 持続 ≥ 700 ms（Aggressive は 450 ms）、強い位相 ≥ 200 ms、PLV ≥ 0.85、N ≥ 0.92、周波数が安定、倍音関係の成分なし |

7. **出力の条件**
   - 最大成分から 35 dB 以内（Aggressive は 38 dB）であること。
   - 突出量がしきい値以上であること。
   - 同じ周波数のイベントの間隔を 150 ms 以上あけます（クールダウン）。
   - 初期カット量は「突出量 − しきい値 + 3 dB」で、範囲は 3〜12 dB です。速い成長経路では 3 dB 上乗せします。

Growth の Low／High は、しきい値を 50／14 dB/s（速い成長）、12／3 dB/s（遅い成長）に変えます。

### 3.1 ノッチ管理
- **Live ノッチ**
  - 検出イベントごとに 3 dB ずつ深くします（Max Cut まで、150 ms 間隔）。
  - EQ をかけた後の残りの信号を再解析するため、ハウリングが止まった時点で深くするのも止まります。
- **リフト（自動解除）**
  - 設定時間が過ぎたら +4 dB/s で解除を始めます。
  - 解除中に再びハウリングが検出されると、その時点から深くし直します。
- **再発メモリ**
  - 解除または奪われたノッチの周波数と、到達した最大の深さを2分間記録します。
  - 同じ周波数で再びハウリングが検出されたら、「前回の深さ − 3 dB」から始めます。
- **スロットを奪う順序**：解除中のもの → 浅いもの → リフト残り時間が短いもの。Lock／Fixed は奪いません。

### 3.2 計算量の削減
- PLV：位相差の cos/sin を保存し、窓内の三角関数の再計算をなくしました。
- 背景推定：ピークのビンだけで、`nth_element` を使って計算します。UI 用の全ビン計算は4フレームに1回です。
- 間引き：96 kHz 以上では解析の計算量がほぼ半分になります。

## 4. ベンチマークの内容（`tests/benchmark.cpp`）

V2 と V3 の両方で、同じソースファイルをビルドして測定しました（V2 はコミット `553ed6a` のソースを取り出してビルド）。条件は 48 kHz、ブロック 256、Release、M4 MacBook Air（arm64）です。

1. **成長するハウリングの検出時間**
   - 背景：ビブラート付きの合成歌唱。5つの音、フォルマントあり、ノイズ −50 dBFS。
   - ハウリング：1.5 秒後に −60 dBFS から 10／30／100 dB/s で大きくなり、−6 dBFS で頭打ちになる正弦波。
   - 周波数：6種類（315.7〜6803.6 Hz）。合計 18 ケース。
   - 測定値：ハウリング開始から最初の正しい検出（±1 %）までの時間。
2. **誤検出率**：30 秒の合成音で、1分あたりのイベント数を数えました。
   - ビブラートのある歌唱
   - まっすぐ伸ばした高い声（2 秒の音）
   - フルート風の音（強い基音、トレモロ、軽いビブラート）
   - オルガン風の和音
   - 話し声とノイズ
   - 歌の音源には、200 ms の相関時間で約 6 cent の自然なピッチ揺らぎを入れています。
3. **周波数誤差**：200〜8000 Hz のランダムな30音。+20 dB/s で成長させ、ノイズ −60 dBFS を加えました。全イベントの誤差を評価しています。
4. **CPU**：解析スレッドの `processNextFrames` と、12本のノッチをステレオでかけたときの処理時間を、音声1秒あたりの ms で測りました。

## 5. 測定結果（V2 → V3）

### 5.1 検出時間（ハウリング開始から、平均）

| モード | 10 dB/s | 30 dB/s | 100 dB/s | 18ケース平均 | 見逃し | 関係ない周波数へのイベント |
|---|---:|---:|---:|---:|---:|---:|
| Advanced V2 | 1837 ms | 681 ms | 324 ms | 947 ms | 0 | 20 |
| **Advanced V3** | **1736 ms** | **600 ms** | **221 ms** | **852 ms** | 0 | **7** |
| Aggressive V2 | 1337 ms | 596 ms | 272 ms | 735 ms | 0 | 215 |
| **Aggressive V3** | 1376 ms | **534 ms** | **191 ms** | **700 ms** | 0 | **23** |
| Classic（Standard） | 3144 ms | 1172 ms | 372 ms | 1563 ms | 0 | 1148 |

ハウリングは −60 dBFS から始まるため、10 dB/s のケースは「聞こえる大きさになるまで」の時間が主な部分です。
- V3 Advanced は、100 dB/s で約 32 % 速くなりました（ハウリングが約 −38 dBFS の段階で検出）。
- Aggressive の 10 dB/s は V2 よりわずかに遅くなりました（+39 ms）。これは誤検出を減らすための条件追加による代償です。

| `processor_test` | − | 合格：実スレッドでのノッチ配置、遅延の報告（144 サンプル）、ホストバイパス時の遅延、Fixed／Lock／Bypass の保存と復元、プリセットの入れ替え、エディタの生成 |

注：成長しない一定振幅の純音が突然現れる場合、V3 は「定常経路」の 700 ms 保持を待ってから反応します。そのため、この人工的なケースでは V2 より遅くなります。実際のハウリングはループゲインが 1 を超えて成長するので、成長経路で検出されます。成長が飽和した後に一定の音が続く場合は、定常経路で検出されます。このテストの「回復」「複数ピーク」項目は、信号を一定振幅のまま長く流すよう延長しました（0.75 秒→1.5 秒、1.17 秒→2.1 秒）。

## 6. 制限事項・試聴が必要な点

- **合成信号だけで評価しています。** 次の項目は Cubase 13 と SM58 を使った実機での試聴が必要です。
  - 実際のマイクとスピーカーの閉ループ
  - 部屋の残響
  - 歌い手が動くことによるループ経路の変化
  - プリアンプのクリップ
- **ストレートトーンの歌唱と、倍音の少ないシンセ・フルート**：V3 で大幅に減りましたが、ゼロではありません（Advanced で数回/分）。高く澄んだ声は倍音が少ないので、Sensitivity を下げるか、サウンドチェックで固定フィルタ（Learn）を作る運用をおすすめします。
- **成長しないハウリング**：一定レベルで鳴り続けるリンギングは、定常経路の 700 ms（Aggressive は 450 ms）を待ってから処理されます。
- **ハウリングと歌の倍音が重なる場合**：倍音保護が優先され、その音符が終わるまで検出が遅れます。
- **Aggressive**：ビブラート歌唱で約 48 回/分の誤イベントが出ます。1回あたりのカットは 3〜6 dB と浅く、ノッチは時間がたつと解除されますが、声の音色が変わる可能性があります。
- **Lookahead (3 ms)**：パニックリミッターだけに効きます。ハウリングの検出そのものは速くなりません。
- **DAW 上での動作確認**：Cubase 13 での読み込み、オートメーション、プロジェクトの保存と再読み込み、オフライン書き出しは、ユーザーによる確認が必要です。コンソールアプリ上での処理系テスト（`processor_test`）は通っています。

## 7. 再現方法

```bash
cmake -S . -B build-v3 -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_C_COMPILER=/Library/Developer/CommandLineTools/usr/bin/clang \
  -DCMAKE_CXX_COMPILER=/Library/Developer/CommandLineTools/usr/bin/clang++ \
  -DFETCHCONTENT_SOURCE_DIR_JUCE="$PWD/build/_deps/juce-src"
cmake --build build-v3 --parallel 8
ctest --test-dir build-v3 --output-on-failure   # 4 テスト
build-v3/fs_benchmark                           # 本資料 §5 の数値
```

V2 の数値を再現するには、`git archive 553ed6a` で取り出したソースに `tests/benchmark.cpp` と `fs_benchmark` ターゲットを加えてビルドします。
